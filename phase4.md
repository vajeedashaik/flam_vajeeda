PHASE 4 — Layout Debugger + Layout Counterfactuals + Layout Health Check

Context: Phase 3 rewrote the resolver to generate multiple candidates, score them
with a deterministic fitness function (src/core/scoring.ts), and produce a
DecisionTrace (src/core/trace.ts) containing every candidate's score breakdown and
per-element reasoning strings. The demo (App.tsx) currently dumps this trace as raw
JSON text below the canvas. Do not modify scoring.ts, candidates.ts, or resolver.ts's
core logic in this phase — this phase is purely about building UI that consumes the
trace/score data that already exists. If you find you NEED to change the shape of
DecisionTrace or ScoreBreakdown to make this phase work, tell me exactly what and why
before doing it — ideally, extend rather than break the existing shape.

GOAL FOR THIS PHASE
Replace the raw JSON dump with three real, readable UI panels, all fed by Phase 3's
existing trace/score data:
1. Layout Debugger — a live decision-trace panel showing per-element reasoning
   ("CTA violated minimum tap target size", "Headline wrapped to 2 lines (safe)").
2. Layout Counterfactuals — shows all candidates and their scores, lets you click a
   non-winning one to see why it lost, and highlights the winner.
3. Layout Health Check — a simplified pass/warn/fail checklist view derived from the
   same ScoreBreakdown data, for at-a-glance readability.

Do NOT build yet: stress lab, self-healing, canvas renderer, degradation slider,
naive-vs-smart comparison, or unknown-surface live input. Those are Phase 5.

REQUIREMENTS — LayoutDebugger.tsx
- Renders DecisionTrace.perElementNotes as a readable list.
- Each note gets a status icon based on content — you decide the simple rule (e.g.
  contains "dropped" → ❌, contains "shrunk" → ⚠️, otherwise → ✓) — document the rule
  you chose in a code comment. Keep the rule simple and deterministic, not a
  judgment call per string.
- Must visibly update immediately when the surface picker changes (same live-update
  behavior as the canvas itself).

REQUIREMENTS — LayoutCounterfactuals.tsx
- Shows every candidate strategy from DecisionTrace.candidateScores with its overall
  score, sorted descending, winner visually marked (e.g. a "chosen" badge).
- Clicking a non-winning candidate shows an explanation string generated by the new
  `explainLoss()` helper in trace.ts. explainLoss() must look at WHICH sub-score
  (constraintViolations, priorityPreservation, visualBalance, tapTargetCompliance,
  renderCost) differs most between the clicked candidate and the winner, and produce
  a plain-language sentence naming that specific sub-score and the gap — e.g.
  "Scored 11 points lower on tap-target compliance — likely a tap target fell below
  the surface's minimum." This must be generated from the actual ScoreBreakdown
  numbers, not a hardcoded string per candidate.
- Write a test in trace.test.ts: given two ScoreBreakdown objects where
  tapTargetCompliance differs most, assert explainLoss() output mentions
  "tap-target" or "tap target" specifically (not a generic string).

REQUIREMENTS — LayoutHealthCheck.tsx
- Derive a checklist from the winning candidate's ScoreBreakdown — map each
  sub-score to a checklist row:
    - constraintViolations ≥ 90 → ✓, ≥ 60 → ⚠, else → ✕  (pick your own thresholds,
      document them in a comment, apply consistently to all 5 sub-scores)
  Rows: "Constraint compliance", "Priority preservation", "Visual balance",
  "Tap-target compliance", "Render efficiency".
- Purely a derived/computed view — no new scoring logic here, just presentation
  thresholds on top of Phase 3's existing numbers.

REQUIREMENTS — App.tsx layout
- Arrange: resolved layout canvas on one side/top, the 3 new panels below/beside it
  (a simple flex or grid layout, no need for polish/styling library — readability
  over aesthetics this phase).
- All 3 panels must update together, live, whenever the surface picker changes —
  verify there's no stale data lingering from the previously selected surface.
